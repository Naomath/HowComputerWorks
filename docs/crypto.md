### 概論
暗号化と復号とに違う鍵を用い、暗号化用の鍵は公開できるようにした暗号方式です。
暗号化と復号に同一の鍵を用いる共通鍵暗号と対比して使われます。
通信の暗号化は重要ですが、その暗号化のための鍵をそもそもどのように配送するか、と言う鍵配送問題を解決する手段の一つです。
現代では暗号化と電子署名の二つで使われます。

### 公開鍵による暗号化
公開鍵暗号での暗号化は、公開鍵で暗号化して、それを秘密鍵で復号します。
一般に、公開鍵暗号での暗号化は計算が重いので、全体の通信の一部のみで使われます。
具体的には共通鍵であるセッション鍵の暗号化です。
セッション鍵は、例えばHTTPSでの具体的な通信の内容を暗号化するなど、メッセージ本体を暗号化しますが、同程度の強さを得るための計算が公開鍵暗号に比べて軽いです。
HTTPS通信の昔の暗号化プロトコルであるSSLでは、初期の頃はセッション鍵をクライアントが生成して、サーバー側の公開鍵で暗号化して共有していました。
このように公開鍵暗号方式と共通鍵暗号方式を組み合わせて用いることを、ハイブリッド暗号方式と言います。

AliceとBobで手順を考えると以下のようになります。

1. AliceがBobへと公開鍵を平文で送る。
2. BobがAliceの公開鍵で、秘密にしたいAliceに送るメッセージを暗号化する
3. Aliceが手元の秘密鍵で、暗号化されたメッセージを復号する

### 電子署名
電子署名での公開鍵暗号の利用は現在でも広く利用されています。
電子署名は以下の二つの手順で実行されます。

- メッセージの署名を作成する
- メッセージの署名を検証する
  
メッセージというのが、通信相手に伝えたい内容のことです。
メッセージを本当である、ということを証明するために電子署名が行われます。
ケースとして、AliceがBobに契約書を送信するとします。
契約書が送られてきて、そこには「Aliceが書きました」とあっても、Bobは以下の2点について確かめたいです。

- この契約書は通信の途中で改竄されていないか
- この契約書を書いたのはAlice本人か

また、ここではその契約書自体を暗号化するかは問題としません。

この際、BobがAliceのものと認めている公開鍵を持っていれば、デジタル署名を使うことができます。
手順は以下の通りです。

1. Aliceが手元の秘密鍵で契約書について暗号化し、その暗号文を署名とする
2. Aliceが契約書と署名を送信する
3. BobがAliceの公開鍵で署名を復号化し、その内容が送られてきた契約書と合致するか検証する
4. 合致していれば、公開鍵のペアとなる秘密鍵の保持者がその契約書を作成したことが保証されるので、Aliceがつくったはずとわかる

ここで、例えば、秘密鍵が漏洩していたり、BobがAliceのものと思っている公開鍵が実は違ったりすると、攻撃者が騙すことができますが、それらへの対策はまた別の問題です。
この電子署名が対策している攻撃は以下のものです。

- 途中で契約書が改竄される
- Alice以外が契約書を送ってくる

一つ目については途中で契約書が改案されて、同じ署名が送られてきた場合、契約書と電子署名が合致しないため、否定されます。
二つ目についても、Aliceの公開鍵では、どちらとも改竄された契約書と電子署名は合致することがありません。

攻撃という文脈と外れますが、否認防止という効果もあります。
Aliceが契約書を書いたことを、後になって「実はつくっていない」否定することを防ぎます。
というのも、その署名はAliceしか作成することができないからです。
もちろん、誰かがAliceのPCを乗っ取って秘密鍵を使って勝手に送信した可能性は残りますが。

実を言うと、メッセージそのものを暗号化して電子署名することは基本的には稀で、メッセージのハッシュ値を署名します。
公開鍵暗号で用いられている、RSAや楕円曲線暗号では暗号化できるメッセージの長さがその鍵長に依存して、決まっているので、無限に長いメッセージを署名することはできません。
ハッシュ関数でメッセージから、固定長のハッシュ値を計算して、そのハッシュに署名します。
手順は以下の通りです。

1. Alicegaが契約書のハッシュを計算し、そのハッシュを秘密鍵で暗号化して署名とする
2. Aliceが契約書と署名を送信する
3. BobがAliceの公開鍵で署名を復号化する
4. Bobが契約書からハッシュを計算し、先ほどの復号結果とハッシュが合致するかをみる
5. 合致していれば、公開鍵のペアとなる秘密鍵の保持者がその契約書を作成したことが保証されるので、Aliceがつくったはずとわかる

最初に紹介した例と本質は変わりません。
ハッシュは誰が例えばSHA-256などの規格が提供されており、ノンスなどがなく、その規定に沿って計算すれば、同じ入力に対しては、どこでも誰でも同じ出力となります。
より細かい話としてはパディングやソルトがありますが、電子署名の本質的にはこの例で十分かと思います。

### 秘密鍵と公開鍵の等価性
「公開鍵による暗号化」ではメッセージを公開鍵で暗号化する一方で、「電子署名」ではハッシュを秘密鍵で暗号化して署名としています。
暗号化のときに使う鍵がそれぞれで違いますが、その理由は、RSA暗号の数学的な仕組みを考えると納得します。
RSA暗号の実際の数学的な仕組みの解説は、どこか別のサイトに任せますが、ある鍵ペアをRSAで作成したときは、どちらを秘密鍵、公開鍵に使うかの区別はなく、二つは等価です。
では、秘密鍵と公開鍵はどのように区別して読んでいるかというと、以下のようになります。

- 手元で保管し、誰にも渡さない鍵が秘密鍵
- 署名や暗号化のために誰にでも渡す鍵が公開鍵

隠しておくか否かの違いで呼び方が違うだけで、数字としての性質の違いはありません。

### Diffie-Hellmanの鍵交換
鍵配送問題への解決策として、現実的に用いられているのは公開鍵暗号とDiffie-Hellmanの鍵交換(DH鍵交換)です。
最新のHTTPSの暗号プロトコルであるTLSでは、まずはお互いの認証を公開鍵暗号の電子署名を用いて行ってから、DH鍵交換で共通鍵を作成しています。
具体的なシステムについては[参考サイト](https://npo-csr.jp/dh%E9%8D%B5%E4%BA%A4%E6%8F%9B%E3%81%A8%E3%81%AF/?doing_wp_cron=1759826793.3629460334777832031250)などを参照してください。

個人的な話ですが、DH鍵交換を初めて知った時は私は感動を覚えました。
根本的に鍵配送問題を解決しているのは、このアルゴリズムのみではないかと考えます。

### 証明書
公開鍵暗号による暗号化が強力であることはわかりましたが、それでも公開鍵をどのように配送するかという問題が残っています。
Aliceの公開鍵として登録しているとBobが思っているものが、実は攻撃者のものであったら、元も子もありません。
そこで、公開鍵そのものをメッセージとして、署名することが考えられます。
この署名とその署名対象の公開鍵のセットを**証明書**と言います。

例えば、BobはCharlieの公開鍵は正しく保持しており、Aliceの公開鍵を欲しいとします。

1. AliceはCharlieに安全に自分の公開鍵を配送する
2. CharlieはそのAliceの公開鍵に、Charlie自身の秘密鍵で署名をして、その署名と公開鍵が書いてある証明書を発行します
3. Aliceはその証明書をBobに送ります
4. Bobはその証明書の署名をCharlieの公開鍵で検証する
5. 合致したら、Bobはその証明書の公開鍵がAliceのものとして信用する

証明書の規格として代表的なX.509には以下の内容が含まれています。
ここでいう認証局はCharlieのことです。

| フィールド名                      | 内容                                                |
| --------------------------- | ------------------------------------------------- |
| **Version**                 | 証明書のバージョン（通常 v3）                                  |
| **Serial Number**           | CA（認証局）が発行時に割り当てた一意の番号                            |
| **Signature Algorithm**     | 証明書署名に使われたアルゴリズム（例：sha256WithRSAEncryption）       |
| **Issuer**                  | 証明書を発行した認証局（CA）の名前                                |
| **Validity**                | 証明書の有効期間（Not Before ～ Not After）                  |
| **Subject**                 | 証明書の所有者（組織名やドメイン名など）                              |
| **Subject Public Key Info** | 公開鍵とそのアルゴリズム情報                                    |
| **Extensions**（v3で追加）       | 様々な拡張情報（例：Subject Alternative Name, Key Usage など） |
| **Signature**               | 発行者による署名データ（改ざん検出・信頼性保証用）                         |

ここで、認証局として完全に信頼されているものはルートCAと言います。
パソコンやスマホは初めから、そのメーカーがルートCAとして信頼するCAの証明書を入れています。
例えば、Apple社が信頼しているルートCAは[https://support.apple.com/ja-jp/121672](https://support.apple.com/ja-jp/121672)から見れます。
SECOMはルートCAとしての活動もしており、上記のサイトにある、Security Communication Root CAはSECOMのことです。

また、この認証局はすべてのサイトを認証するには数が少ないため、中間認証局というのがあります。
中間認証局がルートCAに認証され、そのチェーンが繋がっていき、例えば、自分で作るサイトも証明書を末端の方の中間認証局に発行してもらえます。

実際には、この証明書は公開鍵とその公開鍵を持つ組織についても確認を取ってから発行されるので、**サイトが証明書を持つことは運営元が正しいこと**の証明にもなります。
なんとなく想像できますが、末端のCAになるほど証明書発行までの確認作業も手短で、発行の値段も安いです。
ですので、金融系のサイトなどはより信頼されていると言われる認証局にサイトの証明書を発行してもらいます。

では、実際に証明書の検証をしてみましょう。
ここでは``google.com``のサイトの証明書を検証します。
```bash
mkdir check_certificate
cd check_certificate
openssl s_client -connect www.google.com:443 -showcerts </dev/null
```
出力の一つ目の``-----BEGIN CERTIFICATE-----`` 〜 ``-----END CERTIFICATE-----`` のブロックをコピーして、テキストファイルとして``google.pem``に保存してください。
これが``google.com``に対して、``DigiCert Global G3 TLS ECC SHA384 2020 CA1``という中間CAが作成した証明書となります。
ちなみに二つ目の方は中間CA``DigiCert Global G3 TLS ECC SHA384 2020 CA1``へのルートCAによる証明書です。

``google.pem`` の Issuer 情報から、署名者の中間CA証明書を取得します。
```bash
openssl x509 -in google.pem -text -noout
```
先ほどコピーしたのはバイナリ形式ですが、それを整形して表示しています。
この以下の出力の部分に注目します。
```bash
Authority Information Access: 
                OCSP - URI:http://ocsp.digicert.com
                CA Issuers - URI:http://cacerts.digicert.com/DigiCertGlobalG3TLSECCSHA3842020CA1-2.crt
```
これはその証明書を発行している認証局の情報です。
ここから以下のコマンドでルートCAによる中間CAの証明書を``digi.pem``として取得します。
```bash
curl -o digi.crt http://cacerts.digicert.com/DigiCertGlobalG3TLSECCSHA3842020CA1-2.crt
openssl x509 -in digi.crt -inform DER -out digi.pem -outform PEM
```
今、そしてこの証明書では中間CAの公開鍵が認証情報としてのっているので、その公開鍵で元の``google.com``の証明書を認証します。
```bash
openssl verify -no-CApath -CAfile digi.pem -partial_chain google.pem
```
これで、``google.pem: OK``と出力されたら、``google.pem``という証明書の署名の検証の成功を表します。

### 公開鍵による暗号化と復号
ここでは実際にRSA暗号の公開鍵と秘密鍵で暗号化と復号を体験してみます。

**①　鍵ペアを作成する**

まず、SSH用の鍵ペアを作成します。
``Enter passphrase for "mykey" (empty for no passphrase): ``については2回ともエンターしてください。
これは、秘密鍵を使うときに設定すするパスフレーズの入力を求めていますが、面倒なのでここでは設定しません。

```bash
mkdir kagi_asobi
cd kagi_asobi
ssh-keygen -t rsa -b 4096 -f mykey
ssh-keygen -f mykey.pub -e -m PEM > mykey_public.pem
ssh-keygen -p -m PEM -f mykey
```

- ``-t rsa`` : RSA形式の鍵を生成
- ``-b 4096`` : 鍵長4096ビット（強度が高い）
- ``-f mykey`` : 出力ファイル名（mykeyとmykey.pubが生成される）

これで、秘密鍵: ``mykey``と公開鍵: ``mykey_public.pem``ができます。
2回目からの``ssh-keygen``では鍵のフォーマットをSSH用途から変換しています。

**②　暗号化する（公開鍵で）**

例えば、message.txt に平文を用意します：
```bash
echo "これは秘密のメッセージです" > message.txt
```

次に、公開鍵を使って暗号化します：
```bash
openssl pkeyutl -encrypt -inkey mykey_public.pem -pubin -in message.txt -out message.enc
```

- ``-encrypt`` : 暗号化
- ``-inkey mykey_public.pem`` : 公ｓ開鍵を指定
- ``-pubin`` : 公開鍵入力であることを明示
- ``-in / -out`` : 入出力ファイル

これで``message.enc`` が暗号化されたデータです。

**③ 復号化する（秘密鍵で）**

暗号化したファイルを、秘密鍵で復号化します：
```bash
openssl pkeyutl -decrypt -inkey mykey -in message.enc -out message_decrypted.txt
```
- ``-decrypt`` : 復号化
- ``-inkey mykey`` : 秘密鍵を指定

結果を確認：
```bash
cat message_decrypted.txt
```

ここでは、同一のディレクトリで行っていますが、第三者に``mykey_public.pem``を送って、そこで暗号化してもらい``message.enc``を送り返してもらうこともできます。
Zoomでは私が公開鍵で暗号化しましたが、その暗号内容を送る際に手間取りました。
というのも、暗号メッセージはバイナリ形式で、うまくそれをWSL内で取り込むにはコピペの連続をする必要があったからです。(もちろんもっと軽やかにファイルの送信だけで済む方法もありますが、少々手間がかかるので省きました)
ですので以下の手順を実行しました。

1. 公開鍵``mykey_public.pem``を私がもらう（この時も本当はコピペで頑張った）
2. 私が、``mykey_public.pem``で暗号化し、``message.enc``を作成。
3. 私が、``hexdump message.enc``を実行し、バイナリを16進数でテキスト表示して、コピペでZoomのチャットで送信
4. コーチが、そのテキストを``dump.txt``にコピペ
5. コーチが``xxd -r dump.txt | dd of=message.enc conv=swab``でテキストからバイナリ``message.enc``に戻す
6. 復号する
